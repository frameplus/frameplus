# 숨고 상담 스튜디오 — 인수인계 문서

이 문서 하나로 작업을 이어받을 수 있게 썼다. 읽는 순서는 1 → 2 → 6 → 7이면 충분하고, 3~5는 코드를 고칠 때 찾아보면 된다.

- 저장소: `frameplus/frameplus`, 브랜치 `ccr-d25daa8e-2tro93` (PR #5, 초안)
- 폴더: `soomgo-studio/` — ERP(`src/`, `public/`)와 코드가 섞이지 않는다. `public/` 밖이라 Cloudflare Pages 배포에도 포함되지 않는다.
- 현재 단계: **관리 화면 UI 프로토타입만 완성.** 숨고 연동, 서버 저장, 로그인, 결제, 문자·알림톡 발송은 없다.

## 1. 만들려는 제품

숨고로 영업하는 업체가 구매하는 유료 상담 프로그램이다. 구매자가 자기 숨고 계정으로 로그인하면, 스마트견적으로 연결된 신규 고객의 요청서를 읽고 다음을 처리한다.

첫 상담 10건 발송 → 후속 자동답변 → 고객이 전화·미팅을 원하면 담당자에게 문자/알림톡 → 담당자가 이어받으면 자동답변 중지

| 항목 | 확정 내용 |
|---|---|
| 가격 | 업체당 300,000원. 무료 플랜 없음 |
| 과금 방식 | 일회성 판매 vs 월 구독 **미확정** |
| 첫 고객사 | 프레임플러스(사무공간 인테리어). 기본 홈페이지 `https://frameplus.kr` |
| 카테고리 6개 | 사무실, 교육·학원, 운동시설, 의료·병원, 유리칸막이, 철거·원상복구 |

### 1.1 첫 상담 기본 10건 (채팅방마다)

| 순서 | 내용 | 규칙 |
|---|---|---|
| 1 | 맞춤 인사와 회사 소개 | 이름·지역·업종·공사 내용 반영. 이모지는 자연스럽게. 담당자 연락처 포함. 회사소개서 파일은 보내지 않음 |
| 2 | 업체 홈페이지 | 업체 설정의 홈페이지 주소 |
| 3 | RFP 가이드 | 해당 카테고리에 등록한 최신 파일 |
| 4~9 | 시공 사진 6장 | **한 장씩 개별 발송.** "사진을 보내드립니다" 같은 설명 문구 금지 |
| 10 | 무료 현장 미팅 제안 | 현장에서 무엇을 확인할지 구체적으로 쓰고 가능한 날짜를 물음. 담당자 연락처 다시 포함 |

- 고객이 중간에 "지금 전화 주세요"라고 하면 남은 항목을 계속 보내지 않고 통화 요청을 먼저 전달한다.
- 발송이 끊기면 마지막으로 성공한 항목을 기록한다. **같은 인사나 사진이 두 번 가면 안 된다.**

### 1.2 업종과 공사 내용을 함께 판단

숨고 분류('상업공간 인테리어')만으로는 문구를 정할 수 없다. 학원 전체 공사와 학원 퇴거 원상복구는 같은 교육시설이어도 질문이 다르다.

| 카테고리 | 첫 상담에서 확인 | 현장 미팅에서 확인 |
|---|---|---|
| 사무실 | 근무 인원, 좌석 수, 회의실 수, 입주일 | 좌석 배치, 기존 냉난방 활용, 입주 전 공사 일정 |
| 교육·학원 | 수업 형태, 반별 정원, 강의실 수 | 강의실 크기, 방음, 복도와 상담실 배치 |
| 운동시설 | 운동 종목, 기구 종류, 샤워실 유무 | 기구 간격, 바닥 충격, 탈의실과 급배수 |
| 의료·병원 | 진료과목, 진료실·처치실 수, 장비 | 환자와 직원 동선, 장비 위치, 전기·급배수 |
| 유리칸막이 | 설치 길이·높이, 문 개수, 시야 차단 여부 | 실측, 천장 고정 조건, 출입문 위치 |
| 철거·원상복구 | 철거 범위, 임대인 복구 기준, 인도일 | 존치 시설, 폐기물 반출 경로, 작업 가능 시간 |

**핵심 규칙: 고객이 이미 알려준 내용은 다시 묻지 않는다.** "수원 60평 학원, 예산 7,000만 원 이하, 빠른 착공 희망"이면 평수·예산·일정은 건너뛰고 "강의실은 몇 개가 필요하고, 한 반 정원은 어느 정도일까요?"부터 묻는다.

고객이 적은 예산과 업체가 제시하는 예상 견적은 **별도 항목**으로 관리한다. 예상 견적은 업체가 설정한 평형대별 기준 금액, 포함·별도 공사, 현장 확인 조건에서 나온다.

### 1.3 자동답변과 담당자 알림

| 고객 메시지 | 고객에게 보낼 답변 | 담당자 처리 |
|---|---|---|
| "40평 사무실도 가능한가요?" | 사무실 시나리오로 답하고 빠진 정보 하나를 질문 | 일반 상담으로 기록 |
| "지금 전화 가능하세요?" | 통화 요청을 전달했다고 안내. 번호가 이미 있으면 다시 묻지 않음 | 즉시 통화 요청 알림 |
| "금요일 오후 3시에 현장 보실래요?" | 요청 시간을 확인하고 담당자가 회신한다고 안내 | 희망 일시와 채팅방 링크 전송 |
| "전화 말고 채팅으로 부탁해요." | 채팅 상담을 이어감 | 통화 알림 제외 |
| "예산은 5천이 아니라 6천입니다." | 변경된 예산으로 이어감 | 고객 정보 수정 |

- 알림 내용: 고객명, 지역, 업종, 평수, 요청 원문, 희망 시간, 숨고 채팅방 바로가기
- **같은 메시지로 문자·알림톡이 중복 발송되면 안 된다.**
- 숨고 자체 알림은 새 메시지 감지 수단 후보다. 이 제품의 알림은 통화·방문 요청만 골라 전달한다.

### 1.4 재제작의 첫 완료 기준 (1건)

프레임플러스 계정에 **"내일 오후 3시 현장 미팅 가능할까요?"** 메시지가 오면:

1. 프로그램이 맞는 채팅방을 식별한다
2. 고객에게 접수 답변 1건을 보낸다
3. 소장 휴대폰에 채팅방 링크가 든 알림 1건을 보낸다
4. 관리 화면에 '미팅 요청'으로 기록한다

검증 순서: 실제 안드로이드 숨고 알림에 본문과 답장 기능이 있는지 먼저 확인하고, 부족하면 로그인된 PC에서 처리하는 방식을 검증한다.

## 2. 지금까지 된 것과 안 된 것

| 상태 | 내용 |
|---|---|
| 이 폴더에 구현 | 관리 화면 6개의 UI와 화면 내 상호작용 (목업 데이터) |
| 기존 사이트(chatgpt.site)에 구현 | 6개 카테고리, 카테고리 추가·복사, 고객 요청 5개 입력란, 문구 수정, 파일·사진 업로드·교체·삭제·정렬, 채팅 미리보기, 브라우저 저장·백업. **이 코드는 이 저장소에 없다** |
| 실제 숨고에서 확인됨 | 프레임플러스 계정으로 수원 교육공간 고객 1개 채팅방에 10건 발송 (링크, RFP 엑셀, 사진 6장 개별 발송) |
| 미검증 | 새 채팅 상시 감지, 무인 자동답변, 담당자 문자·알림톡 도착, 계정 재연결, 여러 구매업체 동시 운영, 결제 |
| 판매 전 확인 필요 | 제3자 프로그램의 자동 입력·첨부·연속 발송을 숨고가 허용하는 범위. 한 채팅방에서 발송에 성공한 것만으로는 상업적 이용 허용 여부를 판단할 수 없다 |

기존 사이트와 가장 큰 차이는 **업체별 서버 저장**이다. 한 브라우저에만 저장하면 대표가 PC에서 바꾼 문구를 직원 휴대폰에서 쓸 수 없다. 업체마다 계정·문구·사진·고객 채팅·알림 수신자를 분리하고, 같은 업체 직원은 권한에 따라 함께 쓴다. 아직 구현하지 않았다.

## 3. 실행과 확인

```bash
cd soomgo-studio
python3 -m http.server 8811      # http://localhost:8811
node --check app.js && node --check data.js
```

빌드 도구, 프레임워크, 의존성이 없다. 외부 요청은 Google Fonts 하나뿐이다.

### 4.1 화면과 라우트

주소 해시로 화면을 바꾼다(`#inbox` 등). `app.js`의 `VIEWS[라우트]()`가 HTML 문자열을 돌려주고 `render()`가 `#page`에 넣는다.

| 해시 | 함수 | 화면 |
|---|---|---|
| `#inbox` | `VIEWS.inbox` + `listHtml` / `threadHtml` / `detailHtml` | 상담 목록 + 대화 + 고객 상세 (3단) |
| `#categories` | `VIEWS.categories` + `previewHtml` | 카테고리 문구·질문·견적 기준 편집 + 채팅 미리보기 |
| `#assets` | `VIEWS.assets` + `after.assets` | 전송 순서 1~10번, 사진 교체·삭제·정렬 |
| `#connect` | `VIEWS.connect` | 숨고 연결 상태, 자동응대, 알림 수신자, 알림 기록 |
| `#company` | `VIEWS.company` | 업체 정보, 직원 계정 |
| `#seller` | `VIEWS.seller` | 구매 업체 결제·기간·사용량·발송 실패 |

### 4.2 이벤트 규칙

- 클릭: 요소에 `data-act="이름"`을 달면 `ACT[이름](el)`이 실행된다 (문서 전체 위임, `app.js` 하단).
- 입력: `data-bind`(카테고리 필드), `data-q`(질문), `data-quote`(견적 구간), `data-co`(업체 정보)
- 선택·토글: `data-change="이름"`
- 입력 중에는 화면 전체를 다시 그리지 않고 미리보기만 갱신한다(`refreshPreview`). 전체를 다시 그리면 입력 포커스가 사라진다.
- 사용자 데이터는 반드시 `esc()`로 이스케이프한 뒤 템플릿에 넣는다.

### 4.3 핵심 함수

| 함수 | 하는 일 |
|---|---|
| `fill(tpl, conv)` | 문구의 `{이름} {지역} {공사} {평형} {상호} {담당자} {연락처}`를 치환 |
| `buildSeq(catId, conv)` | 첫 상담 발송 목록 생성: 인사 → 홈페이지 → 가이드 → 사진 n장 → 미팅 제안 |
| `estimate(conv)` | 평수로 카테고리의 평형대 구간을 찾아 예상 견적 문자열 반환 |
| `art(variant)` | 사진 등록 전 자리표시용 도면 스케치 SVG |

### 4.4 데이터 모델 (`data.js`)

서버 스키마를 설계할 때 이 구조를 출발점으로 쓰면 된다.

```
company    { name, manager, phone, site, alertPhone }
team[]     { name, role, perms, phone }
cats[]     { id, name, soomgo, greeting, questions[], meeting, checks[],
             quote[[평형대, 금액]], included, excluded, onsite }
assets[catId] { guide{name,size,updated}, photos[{id,name,variant,src}] }
convs[]    { id, name, region, catId, work, size, budget, budgetNow?, request, schedule,
             status, time, unread, assignee, wish?,
             seq(발송 완료 건수 0~10), sending?, seqNote?, sendFail?,
             known[], missing[],
             msgs[{from: c|auto|human|sys, text, t}],
             alerts[{t, channel, to, type, status}] }
recipients[] { name, phone, channel(문자|알림톡), call, meet }
alertLog[]   { t, who, type, channel, to, status(도착|중복 차단|실패 → 문자 대체) }
vendors[]    { name, field, pay, from, to, link, leads, ai, sms, fail, note }
```

상담 상태 6종(`STATUSES`): `new` 신규, `auto` 자동응대 중, `call` 통화 요청, `meet` 미팅 요청, `human` 담당자 응대, `closed` 종료

**목업 데이터 주의:** 고객·구매 업체는 전부 가상이다. `cats[].quote`의 금액은 화면 구성을 보여주기 위한 예시값이며 실제 단가가 아니다.

## 5. 디자인 기준

레퍼런스(Refero에서 확인): Lemni 인박스(목록·대화·상세 3단), Kit 시퀀스 편집기(편집 + 설정 패널), ManyChat(단계별 메시지와 미리보기), Intercom 채널 설정(연결 상태 카드)

| 규칙 | 내용 |
|---|---|
| 색 | 종이색 바탕 `--paper #f4f2ec`, 먹색 글자 `--ink #17181c`. 토큰은 `styles.css` 상단 `:root` |
| 주홍 `--accent #c2381f` | **사람이 움직여야 하는 일에만 쓴다**: 통화 요청, 이어받기, 재연결, 발송 실패, 읽지 않음. 장식으로 쓰지 않는다 |
| 상태색 | 자동응대 = 청록 `--auto`, 미팅 = 황토 `--meet`, 담당자 = 남색 `--human` |
| 글꼴 | IBM Plex Sans KR. 숫자·시각은 IBM Plex Mono(`.num`) |
| 아이콘 | `app.js`의 `ICONS` 인라인 SVG. 이모지를 아이콘으로 쓰지 않는다 (고객에게 보내는 문구 안의 이모지는 내용이므로 허용) |
| 반응형 | 1240px 이하: 상세·미리보기가 오른쪽 서랍으로. 820px 이하: 사이드바가 서랍, 상담 목록 → 대화 단일 컬럼 |
| 문구 | 버튼은 동작을 말한다("담당자가 이어받기"). 프로토타입이라 실제로 안 되는 동작은 토스트로 그렇게 알린다 |

피해야 할 것: 같은 크기 카드 나열, 큰 숫자 + 작은 라벨 통계 블록, 제목 위 작은 라벨, 그라데이션 글자, 카드 좌측 색 띠, 불필요한 모달.

### 6.3 프로토타입에서 알려진 한계

- 새로고침하면 모든 변경이 사라진다.
- 사진 교체는 `URL.createObjectURL`로 그 브라우저에만 보인다.
- 상담 목록의 시각·"2분 전 수신" 등은 고정 문자열이다.
- 카테고리 삭제 기능이 없다(추가·복사만 있다).
- 알림 수신자 이름·번호 입력란은 상태에 반영되지 않는다.
- 응대 시간, 자동답변 중지 조건 선택은 표시만 한다.
- 견적 금액 자동 제시 문구(고객에게 보내는 답변)는 화면에 없다. 고객 상세에 예상 견적 값만 표시한다.

## 7. 작업 규칙

- `soomgo-studio/` 밖의 파일(ERP)은 이 작업으로 고치지 않는다.
- 실제 고객 이름·전화번호·숨고 계정 정보·API 키를 저장소에 넣지 않는다. 목업은 `박*현`, `010-0000-0000` 형태를 유지한다.
- 숨고에 실제로 메시지를 보내는 코드는 프레임플러스 계정으로만, 사람이 지켜보는 상태에서 시험한다. 다른 업체 계정으로 시험하지 않는다.
- 문자·알림톡은 과금된다. 시험 발송은 수신 번호를 고정하고 건수를 제한한다.
- 화면을 고친 뒤에는 1440px과 390px 폭에서 6개 화면을 열어 콘솔 오류와 가로 넘침이 없는지 확인한다.
- 한국어 UI 문구는 존댓말, 한 문장에 한 가지 내용.
